# Command reference

Everything below is run by your agent; you normally never type these commands. This page is for looking things up, for troubleshooting and for engine developers. For an overview, see the [README](../README.md).

Commands are written as `python tools/graph.py <command>` from the engine folder (agents use `python "$VAULT_ENGINE/tools/graph.py" <command>`).

## Structure
| Path | Content |
|---|---|
| `tools/graph.py` | Search, propagation, learning, guard, leakcheck. Python standard library only. |
| `tools/feedback.py` | Optional, leak-free feedback (see below). |
| `tools/hooks/` | Guard hooks for data repos (`core.hooksPath` points here) |
| `tools/update.py` | Checks for and applies engine updates on the stable channel |
| `tools/schema.py` | Vault data schema version and migrations |
| `tools/claude-agents/` | Claude Code subagent definitions (copied into `~/.claude/agents/`, or `$CLAUDE_CONFIG_DIR/agents/`) |
| `defaults/` | General notes. A note at the same path in the data repo overrides these. |
| `templates/` | Skeleton for a new data repository |
| `.githooks/` | This repo's own hooks: `leakcheck` |
| `tests/` | `python -m unittest discover -s tests` (or `python tests/run_shard.py --jobs 3` to run it as 3 parallel shards) |

## Setup
1. Clone the engine and switch to the latest release: `git describe --tags --abbrev=0` in the engine folder prints it, then `git checkout <that tag>`. Without this step the engine stays on `main`, the development channel, and never announces new versions (see "Versions and updates"). Python 3.10+ is enough. Optional: Ollama + `ollama pull bge-m3` (without it, only keyword matching is used).
2. Create a data repo: `python tools/graph.py init <data repo path>`, in a folder that is not inside another git repo (`init` refuses one, so it never changes that repo's settings). This copies the contents of `templates/` (without overwriting existing files; its `.gitattributes` keeps line endings LF, so Git for Windows doesn't warn about CRLF on every commit), initializes a git repo (branch `main`, with an initial `chore: initialize vault` commit if git has an identity configured — otherwise `init` tells you how to set one), points `core.hooksPath` at this engine's `tools/hooks` folder, and writes the feedback preference into `vault.config.json` (feedback is `off` by default — opt-in). In a TTY, if `--yes` is not given, it prompts for missing values; they can also be set manually with `--feedback`, `--feedback-mode`, `--project-root` (repeatable), and `--yes`. Per-computer project roots (`--project-root`) are written to `<data repo>/.graph/machine.json`, not to the shared `vault.config.json` — see "Project recognition" below. On a second computer, do step 1 there too, clone your existing data repo instead of this step and run `git config core.hooksPath <engine>/tools/hooks` in it. Don't run `init` on it (it recreates template files you deleted). If this computer keeps its projects somewhere other than the folder that holds the engine, run `python tools/graph.py machine --data <data repo path> --project-root <path>`: it writes only this computer's `.graph/machine.json`.
3. Connect the engine to the data repo: `python tools/graph.py setup [--data <data repo path>]`. This sets environment variables: on Windows, persisted with `setx`; on macOS/Linux, after asking, it writes `VAULT_ENGINE`/`VAULT_DATA` into your shell startup file (`~/.zshrc`, `~/.bashrc`/`~/.bash_profile` on macOS, your fish config, or `~/.profile`) inside a `# >>> vault-engine >>>` block — restart your terminal(s) and any coding agent afterward so they pick up the new values. It also names this computer for its learned-links file (see "Machine name" below), copies `tools/claude-agents/*.md` into `~/.claude/agents/` (a file there with your own content is kept: in a terminal `setup` asks and keeps a `.bak` copy before replacing it, otherwise it skips it), and, for each project root that isn't itself a git repo, writes a `@<data repo path>/AGENTS.md` line into `CLAUDE.md`. Running it twice changes nothing. `--user-level` also adds a one-line pointer to `~/.claude/CLAUDE.md` and `~/.codex/AGENTS.md`. `--no-env`, `--no-machine`, `--no-agents`, `--no-routing`, `--yes` skip/automate the corresponding steps. With `--yes` it doesn't ask before writing the shell startup file.
4. Fill in the notes under `profile/`.
5. Optional: fill in `profile/` from a short set of questions (chat/notes/code language, detail level, explain level, what to always ask before doing). Through an agent: `python tools/graph.py onboard --questions` prints them as JSON; the agent asks you, then `onboard --answers <file.json> [--data <data repo path>]` writes the answers (a UTF-8 file, with or without BOM). In a terminal, `onboard` alone asks them itself; without a terminal (an agent, or stdin redirected from `NUL`/`/dev/null`) it stops without writing anything. Notes you already filled are kept unless you add `--force`. It commits the notes it wrote (`chore: fill in profile`) in the data repo; push them if it has a remote.
6. Check: `python tools/graph.py doctor [--data <data repo path>]` — one check per line (`OK`/`WARN`/`FAIL`); any `FAIL` sets the exit code to 1. It also warns while the profile is still the unfilled skeleton, and when files the engine writes in the data repo (`vault.config.json`, `AGENTS.md`, `.github/workflows/vault.yml`, `.graph/learned/`, the profile notes, ...) have uncommitted changes, with the commit command. It also warns when the vault's `.gitignore` lacks lines of `templates/.gitignore` (fix: `migrate`) and when git tracks files that `.gitignore` ignores (`git rm --cached`). Every engine command that writes one of these commits exactly the files it wrote (`git commit --only`, so what you staged stays staged) and never pushes.

7. Live check (Claude only): `python tools/graph.py doctor --live` runs a probe task through the real `context`, `show --body`, `reinforce --task <id> --outcome ok` (no note ids) and `stats --retrieval` code paths and checks the fields they log (`core`, `scores`, `fallback_reason`, `task`, `from_omitted`, `outcome`), then checks that the last non-internal `subagent_stop` record in `usage.log` has an `agent_type` (`WARN` with a hint if there is none yet: run any subagent once). Claude Code internal agents have no transcript or meta file; the hook logs them with `"internal": true` and the check skips them (records written before this flag need one fresh subagent run). One `OK`/`FAIL`/`WARN` line per check, exit 1 on any `FAIL`. The probe's `usage.log` lines carry `"probe": true` and a `probe-` task id; `stats` (also `--retrieval`) and the feedback metrics ignore them. The probe changes no learned weight, triggers no decay and makes no git commit.

The terminal or agent that ran `setup` doesn't see the new environment variables until it is restarted; pass `--data` to `onboard` and `doctor` until then. On Windows, commands that need the data repo also fall back to the `VAULT_DATA` that `setup` saved for your user (with a note to restart).

## Updating another computer

After changes on one computer, on every other computer that shares the data repo:

```
git -C <data repo> pull --rebase --autostash
python <engine>/tools/graph.py update --all            # engine (any channel), migrate, setup, Claude/Codex agents, hooks, models, then doctor
python <engine>/tools/graph.py user-config --install   # if doctor reports config drift
```

Every installer backs up a file before changing it and does nothing on a second run.

## Project discovery
`tools/discovery.py` scans the git repos next to the engine (or under this computer's project roots, see "Project recognition") and finds which projects have no notes yet. It only reads lightweight metadata (the README's first line, a file-extension count, the last commit date, the remote's host part only); code is never indexed and nothing leaves the machine. The `exclude` list (names or globs) in `vault.config.json` excludes a project from the scan on every computer sharing the vault; a `.vaultignore` file in a repo does the same. The result is cached for 1 hour in `<data repo>/.graph/projects.json` (not committed). Usage: `python tools/graph.py projects` (table, shows `notes:no (skipped)` for skipped ones), `--json` (adds a `skipped` field), `--missing` (only projects without notes and not skipped, with a suggestion at the end), `--refresh` (ignore the cache), or `--ask` (a report for the agent: lists candidates plus instructions to ask the user which should get notes -- the engine never writes project notes itself). `--skip NAME [NAME ...]`/`--unskip NAME [...]` add/remove names from this computer's own skip list, stored in the gitignored `<data repo>/.graph/machine.json` (`skip_projects`) -- unlike `exclude`, this only affects this computer, so another one sharing the vault is still asked about the same project.

## Project recognition
`context` finds the project from the directory it's run in and uses `projects/<name>/` notes as the starting point. Project roots are per computer, since two computers sharing one data repo can keep their code in different places. Lookup order: `<data repo>/.graph/machine.json` (`{"project_roots": ["..."]}`, gitignored, written by `machine --project-root`, `init --project-root` or `init`'s interactive prompt) first; then, for old vaults, `project_roots` in the shared `vault.config.json`; if neither is set, the engine's parent folder is used. Roots that don't exist on this computer are skipped, so another computer's path left in the shared config never hides this computer's projects; `migrate` moves an old shared `project_roots` into this computer's `.graph/machine.json`. Set manually with `--project <name>` or `--no-project`. The total `context` output is capped at 28000 UTF-8 bytes (`CONTEXT_OUTPUT_CAP`), because Claude Code's Bash tool writes longer output to a file and shows the model only a short preview. Over the cap, whole notes are dropped (task notes first, then project entry notes, lowest activation first) and one `<!-- omitted over output cap (N bytes > 28000): ids -->` line names them, followed by the `show --body <id>` line. Core notes and the fixed lines are never dropped; if they alone exceed the cap, the output ends with a `WARN: core notes alone exceed output cap` line (exit 0).

## Machine name
Learned links are saved per computer in `<data repo>/.graph/learned/<name>.json`, which `reinforce` and `decay` commit on their own (only that file), so two computers never edit the same file and the next `git pull --rebase` finds nothing uncommitted. Decay runs on its own: when `reinforce` finds that more than 7 days have passed since this computer's last decay (timestamp in the gitignored `.graph/last-decay`, also updated by a manual `decay`), it first weakens the learned edges by 5% and prints one `auto-decay:` line; the change lands in the same learned-links commit. The first `reinforce` after an upgrade only records the timestamp, so nothing decays right away. Older versions used the hostname as `<name>`, which can reveal a person or an employer. `setup` now asks for a neutral name (default `pc-` and four random characters, also used with `--yes`) and saves it as `"machine"` in this computer's gitignored `.graph/machine.json`. A computer that already has a learned file under its hostname keeps using it; nothing is renamed automatically. Show or change the name with `python tools/graph.py machine [--data <data repo path>] [--name <name>]`; after a change, `git mv` the old file to the new name to keep adding to it. The `VAULT_MACHINE` environment variable, if set, wins over both.

## Status note rotation
`python tools/graph.py rotate <project>` keeps `projects/<project>/<project>-status.md` short. The status note holds at most 5 dated items (top-level bullets that start with `- YYYY-MM-DD`, with their indented continuation lines) under its "Where we are" section. `rotate` moves the oldest surplus items, oldest first and unchanged, to the end of the "Journal" section of `<project>-history.md`. It creates the history note (linked to the status note) when it is missing. Undated bullets and all other text stay where they are, and existing history is only appended to.

`rotate` is idempotent: with 5 items or fewer it prints `nothing to rotate` and writes nothing. `--dry-run` prints what would move and writes nothing. It commits exactly the two notes it wrote (`chore: rotate <project> status note`) and never pushes; `--no-commit` leaves them in the working tree. Section names come from `vault.config.json`: `{"status_note": {"recent_heading": "Where we are", "journal_heading": "Journal"}}` (these are the defaults; set them when your notes use other headings, matched case-insensitively).

`lint` reports an error for a status or overview note whose body is over 5,000 characters. `reinforce` prints one `WARN:` line, with the exact `rotate` command, when the project it runs in has a status note over that size or with more than 5 dated items. `rotate` does not shorten an overview note or other sections: move that content to the history note by hand.

## Tasks
`python tools/graph.py tasks [--status <status>] [--project <project>]` lists the task notes under `inbox/`, sorted by project and then by status. The six statuses, in order: `open`, `ready`, `in-progress`, `review`, `blocked`, `done`. A task goes `open` → `ready` → `in-progress` → `review` → `done` (or `blocked`). `ready` means the spec is complete; `review` means a PR is open and waits for the human. Only `done` tasks stop loading into `context` output.

Tasks have no budget field: each worker role has its own turn cap (see [agent-setup](agent-setup.md)); an old `budget:` line in a task file is ignored. The task template (`templates/inbox/_template.md`) also has a `## Acceptance` section: a fenced code block with exactly one line (join several commands with `&&`), the command whose exit code decides pass or fail (`human` for non-code work).

`lint` checks tasks:
- Error: a `ready` task with no `## Acceptance` block (a fenced block with at least one non-blank line), or whose block has more than one non-blank line (join the commands with `&&` on one line; queue-runner, codex-worker and verify refuse such a block instead of running only its first line).

## Task verification
`python tools/graph.py verify --task <id|path> --diff <file> [--acceptance-output <file>]` is the mechanical part of the `worker-verify` agent's check. `--task` is a note id or the path of a task file; `--diff` is a unified `git diff` saved to a file; `--acceptance-output` is the output of the task's `## Acceptance` command. It prints `PASS` or `FAIL`, then one `- ok:` / `- fail:` / `- human:` line per item, and exits 0 on PASS and 1 on FAIL. Items: the acceptance output is green (last line `OK`, or `exit 0`, and no `FAILED` or non-zero exit; without `--acceptance-output` the item is reported as `- human:` (needs a human check) and does not by itself make the result FAIL; with it, a red output still fails); no changed file matches the task's exclusions (lines under a `Files not to touch` / `Dokunulmayacak dosyalar` heading and bullets starting with `Exclude:` / `Hariç:`; a pattern with `*` or `?` is a glob, one ending in `/` is a folder); the diff is not empty. It only reads the files you give it: no git command, no `usage.log` entry, no learning.

## Codex worker
`python tools/graph.py codex-worker (--task <id|path> | --prompt-file <file>) --worktree <dir> [--out <dir>] [--profile worker-low|worker-medium] [--model <m>] [--effort <e>] [--instructions <file>] [--acceptance <cmd>] [--base <ref>] [--timeout <s>] [--config-trim ignore-user-config|blank-instructions|none] [--commit] [--commit-message <text>] [--allow-main] [--dry-run] [--json] [--codex <exe>]` is what the orchestrator runs directly in the background (the `codex-worker` skill, no relay subagent): it hands one task to Codex (`codex exec -s workspace-write --json`, never `danger-full-access`) inside a linked git worktree. The worktree must be a linked worktree (a main checkout is refused, and so is a branch named `main` or `master` unless `--allow-main`). The prompt is fixed worker rules plus the task body (or the raw prompt file) plus `--instructions`; it goes to Codex on stdin and is saved as `<out>/prompt.md`. `--profile` (default `worker-medium`) selects `tools/codex-agents/<profile>.toml`, the single source of model, effort and the worker rules (`developer_instructions`); `--model` / `--effort` override the profile's values, and a missing profile file is an error (exit 2). Defaults: profile `worker-medium`, base `origin/main`, timeout 1800 s, `--out` `<tmp>/vault-codex-worker/<task>-<time>`. `--config-trim` keeps `~/.codex/config.toml`'s `developer_instructions` (the vault rules, a large input-token cost on every run) out of the worker; the wrapper always passes the profile's `developer_instructions` as `-c developer_instructions=<TOML string>` (so the default `blank-instructions` and `none` add no extra flag, and the prompt itself holds only the run-specific rules). `ignore-user-config` is cheaper but also drops the `[windows] sandbox` setting, after which the sandbox cannot write files on Windows. After the run it prints (and saves as `<out>/report.md`) the status, the changed files and commits from git, Codex's own decisions / evidence / blockers, the acceptance command's exit code and last line (run by the tool in the worktree), token totals summed over all turns, and the Codex thread id. Exit code 0 when the run completed (any STATUS), 2 for argument or worktree errors, 3 when `codex` is missing or the run timed out. `--dry-run` prints the profile, model, effort, the profile's developer instructions, the command and the prompt, and runs nothing. The report and `--json` carry `profile`, and the `codex_exec` usage event records it. Codex's sandbox cannot write a linked worktree's git dir, so it cannot commit; with `--commit` the wrapper itself runs `git add -A` and `git commit` in the worktree after the run (message `--commit-message`, default `wip(codex): <task id or prompt>`), and the report and `--json` (`wip_commit`) show the short hash, `none (clean)` or `failed: ...` (a failure is a blocker line, the exit code is unchanged).

The `models` command also sets the verifier: `--worker-verify <model>` and `--worker-verify-effort <level>` (see [agent-setup](agent-setup.md)).

## Queue runner
`python tools/graph.py queue-runner [run] [--dry-run] [--print-schedule] [--time HH:MM] [--timeout <s>] [--claude <exe>]` (also `python -I tools/queue_runner.py ...`) is the queue runner that turns the oldest `ready` task into a PR without a human prompt. One task per run; merging stays with you. It refuses to run (exit 2) unless this computer's `.graph/machine.json` has a `queue` block with `"enabled": true`, a non-empty `projects` allowlist and a positive dollar ceiling per task:

```json
{"queue": {"enabled": true, "projects": ["vault-engine", "diet-tracker"],
           "budgets_usd": 5, "max_turns": 80}}
```

`max_turns` is optional (default 80); there is no default for `budgets_usd`, so without it the queue never runs. Both are single numbers; the old per-class objects (`{"S": 2, ...}`) are refused with the new shape in the error message. A run: pulls the data repo (when it has a remote), picks the oldest `ready` task (by `created`, then id) of an allowed project that has an acceptance command (not `human`); none: prints `queue empty` and exits 0. It claims the task (status `in-progress`, commit, push; a rejected push means another machine claimed it, so the run aborts without starting), resolves the project folder as `<project root>/<project>` (project roots as for `projects`), and creates `<repo>/.claude/worktrees/queue-<task number>` on `feat/queue-<task slug>` from `origin/main`. It then runs `claude -p <prompt> --permission-mode auto --max-turns <max_turns> --max-budget-usd <budgets_usd> --output-format json` there (argv list, no shell; `--claude` or `VAULT_CLAUDE_BIN` or PATH; `--timeout` default 5400 s). The runner itself then runs the acceptance command in the worktree. Green: it pushes the branch, opens the PR with `gh pr create` (task id, acceptance output tail, cost and turns, the orchestrator's result), sets the task to `review` and appends the PR link to its `## Log`. Red acceptance, a budget hit (`error_max_budget_usd`, `error_max_turns`), a claude error or a timeout: status `blocked` and a Log line with the reason and evidence (acceptance output, subtype, cost, branch with the WIP commits). The task-file change is committed (and pushed) in the data repo.

Each run writes one `queue_run` event to `usage.log` (task, project, outcome `pr`|`blocked`|`empty`|`refused`, duration_s, turns, tokens, usd, reason, pr); `stats` summarizes them under "queue runs". `--dry-run` prints the pick, plan and argv and changes nothing. `--print-schedule` prints a Windows `schtasks /Create` command and a cron line for a daily scheduled run (default 02:00) with `VAULT_DATA` set, and installs nothing; the OS scheduler is used so the permission mode is passed by flag on every run and cannot fall back to Manual. The schtasks `/TR` value (`cmd /c set "VAULT_DATA=..."&& "<python>" -I "<script>" run`) must not exceed 261 characters; a longer one makes `--print-schedule` fail with an error asking for a shorter engine or data path. The acceptance command is handed to the shell as one string (`cmd.exe` on Windows, `sh` elsewhere, as in `codex-worker`), so write it to work in both (`&&`, double quotes); child processes get no stdin. The worktree folder `.claude/worktrees/` is added to the project's local `.git/info/exclude`, so the main checkout stays clean.

The tests in `tests/test_queue_runner_boundaries.py` run the outside boundaries for real (shell, local git with a bare origin, Windows or POSIX command-line parsing of the schedule line, an end-to-end run); only `claude` and `gh` are fake scripts. The `claude -p` output contract is pinned by three recorded files in `tests/fixtures/claude_p/` (`success.json`, `error_max_turns.json`, `error_max_budget_usd.json`) taken from real runs with `session_id`, `uuid` and `credential_expires_at` removed. To regenerate them (about 0.3 USD at list price; `--max-turns` is not listed in `claude --help` but is accepted), run each command once from an empty temp folder and save stdout: `claude -p "Reply with the single word: ok" --output-format json` (exit 0), `claude -p "Use a tool to list the files in the current directory, then answer." --max-turns 1 --output-format json` (exit 1), `claude -p "Reply with the single word: ok" --max-budget-usd 0.0001 --output-format json` (exit 1); then delete those three keys, pretty-print with two-space indentation and run `python -m unittest tests.test_queue_runner_boundaries`.

## Retrieval evaluation
`python tools/graph.py eval --set <file.jsonl> [--no-semantic] [--k 3,5,10] [--split dev|holdout|all] [--json]` measures how well `context` finds the right notes. The set is a JSONL file, one query per line: `{"task": "...", "ts": "...", "query": "...", "relevant": ["note-id", ...], "split": "dev"|"holdout"}`. A relative `--set` path is resolved against the current directory.

For each query the ranking is the list `context` builds before its token budget (default threshold and depth; notes it would omit over budget keep their place, after the loaded ones). Two deliberate differences: core notes are left out of the ranking and out of the query's relevant set (they load for every query; a query with no other relevant note is skipped and counted), and projects are not seeded from the working directory, so the result does not depend on where you run it. Nothing is logged: no `usage.log` event, task id or learned-link change. Only the embeddings cache can be refreshed, as `index` does; `--no-semantic` writes nothing.

Output is one table for the chosen split (default `all`) with a `keyword` and a `semantic` column: n, recall@k for each k (the share of a query's relevant notes in the top k, averaged over queries) and MRR (1 / rank of the first relevant note, 0 if none). `--no-semantic` prints only the keyword column. When Ollama is unavailable the semantic column reads `n/a` with the reason and the command still succeeds. `--json` prints the same numbers as `{set, split, k, modes: {keyword|semantic: {available, skipped, splits: {<split>: {n, recall: {<k>: ...}, mrr}}}}}`.

## Feedback
`tools/feedback.py` optionally sends feedback from your setup to the engine's developers (as a GitHub issue). It is off by default; you must explicitly turn it on before anything is sent.

Levels (in `vault.config.json` under `"feedback": {"level": ..., "mode": ..., "repo": "owner/name"}`):
- `off` (default): nothing is sent.
- `metrics`: only counts and fixed categories are sent -- engine version, OS, Python version, note-count bucket (`<25`, `25-100`, ...), `context`/`reinforce` usage counters, per-agent distribution. Note IDs, query text, file paths, and machine names are **never** sent. Sent at most once every 7 days.
- `reports`: in addition to the above, short free-text notes queued with `feedback add --kind friction|bug|idea --command <command> --summary "..." [--details "..."]` are also sent (summary max 200, details max 1000 characters).

`mode`: `ask` (default; shows a preview first, the agent asks the user, confirmed with `feedback send --yes`) or `auto` (the engine sends in the background at most once a day after `reinforce`).

The target repo is taken from the `feedback.repo` field, or otherwise from the engine's `origin` remote; if neither is set, sending is disabled (no error).

Free text (summary/details/command) is filtered twice, once when queued and once right before sending: it's scanned against the same guard patterns used for notes (Turkish national ID numbers, IBANs of any country, card numbers, phone numbers in Turkish, US, UK and international `+<country code>` formats, dashed US Social Security numbers, email, tokens, passwords), the home directory path, the git identity, terms from `.git/info/vault-denylist`, and project names in the data repo. If anything matches, the text is **never** sent or printed; only the match type (e.g. "IBAN") is reported, and the content is moved to `.graph/feedback/quarantine/`.

Commands:
- `feedback status` -- active settings, target repo, queue/quarantine counts, last send time.
- `feedback list` -- shows exactly what would be sent, as JSON (does not send).
- `feedback send [--yes]` -- sends what's queued.
- `feedback set --level ... [--mode ...] [--repo ...] [--machine]` -- writes settings. With `--machine`, writes to a machine-local, gitignored `.graph/machine.json` (overrides the shared setting in the data repo) — useful on a sensitive machine.

To turn off: `feedback set --level off` (or with `--machine` for a specific machine).

## CI (GitHub Actions)
- Engine repo: on every push and PR, tests run (Ubuntu: Python 3.10 and 3.13, Windows: 3.13) along with `leakcheck` (files + commit messages).
- Data repo: the `.github/workflows/vault.yml` shipped by `init` uses the engine as a composite action (`uses: <owner>/vault-engine@<ref>`): guard, commit messages, and note lint. This way commits pushed from the cloud or a phone are checked too. `init` pins `<ref>` to the installed engine's release tag on the stable channel, or `main` otherwise; `update` moves that pin to the new tag when it switches versions and commits the changed `.github/workflows/vault.yml` in the data repo; push it afterward.
- The engine is public, so this works as-is. If you instead use a private fork of the engine, do this once in that repo: Settings > Actions > General > Access → "Accessible from repositories owned by the user". Or via the CLI: `gh api -X PUT repos/<owner>/vault-engine/actions/permissions/access -f access_level=user`

## Versions and updates
- Releases follow [SemVer](https://semver.org/) and are listed in [CHANGELOG.md](../CHANGELOG.md). While the version is 0.x, a minor bump (0.1 → 0.2) may change config, commands or the data layout; its changelog entry then has **Upgrade notes**.
- Current version: `python tools/graph.py --version` (also the first line of `doctor`).
- **Stable channel** (the default for new installs): the engine checked out at a release tag, as the install guide does. Don't run `git pull` there — HEAD is detached at a tag, not on a branch.
- **Dev channel**: the engine on a branch. `update` works there too: on `main` with a clean tree it runs `git fetch` and `git pull --ff-only` without asking, then the same steps as on stable. On another branch, with local changes, or when `main` cannot fast-forward it stops and prints the exact command that fixes it; it never creates branches, merges or rebases. `doctor` warns on a dev checkout with the command that switches to the latest release (`update --to <tag>`); on the engine developer's computer mark it once with `python tools/graph.py machine --engine-developer on` (stored in the gitignored `.graph/machine.json`) and the warning becomes an INFO line. Existing installs are never switched automatically.
- Never update the engine by hand (`git pull`/`merge`/`checkout`, ad-hoc branches); use `update` on every channel.
- On the stable channel the engine (0.3.0 and later) checks the newest remote tag with `git ls-remote` (nothing is sent) at most once a day, after `reinforce`; `doctor` checks every run. If a newer version exists, `doctor` shows a `WARN` and `context` prints one line telling the agent to ask the user once. Turn this off with `"updates": {"check": false}` in `vault.config.json`, or in `.graph/machine.json` for a single computer. Separately, if `~/.claude` (or a registered Claude config dir, see `claude-dirs` below) exists, `context` also prints one line when the Claude Code hooks, model settings or subagent files on this computer are out of date, telling the agent to ask the user once and then run `update --all`. If `~/.codex` exists, it checks Codex hooks and worker TOMLs for missing or stale files, and warns if top-level `model` or `model_reasoning_effort` is absent or invalid in `config.toml`. It does not know the user's preferred model, so it cannot detect drift from that preference. `update --all` (or `python tools/graph.py codex-hooks --install`) adds missing hooks and worker profiles; it also replaces worker profiles that are an unedited earlier shipped version and keeps edited ones. `update --agents` (or a yes at its prompt) refreshes the Codex worker profiles the same way, but only when `<CODEX_HOME>/agents` already holds a shipped worker, and never touches `hooks.json`. The Codex hooks are `context-warn`, `delegation-warn` and a `PreToolUse` `agent-guard` (matcher `Agent|spawn_agent`) that denies spawning anything but the shipped `worker-*` profiles or with a different model/effort. Honest caveat: an experiment on Codex CLI 0.159.2 did not demonstrate that Codex enforces a PreToolUse deny for sub-agent spawns; the guard is installed for when the CLI honors it. `doctor` prints an INFO line when `codex --version` differs from the version stored in `.graph/machine.json` (`codex_deny_tested_version`, machine-specific, gitignored) or none is stored; `python tools/graph.py codex-hooks --probe-deny` re-tests it with one throwaway `codex exec` in a temporary git dir (project `.codex/hooks.json` with a PreToolUse deny hook, prompt "create probe.txt with content x"; your real Codex config is untouched; skipped if codex is missing), reports whether the hook fired and the write was blocked, and records the version and result (including an inconclusive run). `python tools/graph.py codex-hooks --ack-deny` records the current version as acknowledged without running the probe, to dismiss the INFO line. `doctor` also warns on Python older than 3.11, where Codex `config.toml` user-config items (`tomllib`) are unavailable. Installs made before this guard existed show as stale until `--install` is rerun. The installer backs up `hooks.json` before changing it, merges unrelated hooks, and leaves customized worker files in place.
- Claude Code config dirs: Claude Code reads `$CLAUDE_CONFIG_DIR` when set, else `~/.claude`, and a computer can have several. The engine keeps the ones it manages in this computer's gitignored `.graph/machine.json` (`~/.claude` is always included; a dir is recorded whenever an engine command runs with `CLAUDE_CONFIG_DIR` set, except dirs in the system temp folder; registered dirs that no longer exist are skipped and `doctor` shows one INFO line suggesting `claude-dirs --remove`). `claude-hooks --install`, `models --apply` and `update --claude-hooks/--models/--agents` act on every registered dir (`--settings`/`--agents-dir` target just one). Other `.claude*` dirs under your home folder that look like config dirs are only reported, never added on their own: `python tools/graph.py claude-dirs [--list | --ask | --add <path> | --remove <path>]`, and `doctor` warns about them. `stats --tokens` reads `<config dir>/projects` of the active dir. Model tables show call, token and cost shares; Claude also splits calls into main-session and subagent usage. The JSON keeps Claude's `calls_pct`, `total_pct`, `cost_pct`, `main_calls`, and `sub_calls`. For Codex, each `codex.by_model[]` row includes `calls`, `calls_pct`, `total_pct` (token share), `cost_pct`, `est_usd`, `main_calls`, `subagent_calls`, `main_tokens`, `subagent_tokens`, and their split percentages. Codex `cost_pct` is each priced model's share of the subtotal for models with known prices. When `cost_basis` is `partial_api_list_estimate` and `cost_estimate_status` is `partial`, this subtotal excludes unpriced model usage. Top-level JSON adds `cost_basis`, `est_total_usd`, `model_attribution`, `agent_split_status`, `main`, and `subagents_total`. `stats --tokens --session <id|current>` breaks down one session by model and separates the main session from subagents, with one row per subagent run. Its JSON includes `models`, `totals`, `main`, `subagents_total`, `subagents`, and `agent_breakdown`; each subagent row has its session ID, role, model list, calls, total tokens, token share, and estimated USD. `est_usd` is an estimate at standard OpenAI API list rates, not a Codex or ChatGPT subscription charge. When model or agent attribution or cost is incomplete, status fields report partial/unknown and affected counts or costs are `null` rather than guessed. Claude session reports also show estimated USD (`--since` is ignored). `current` uses `CLAUDE_CODE_SESSION_ID` (Claude Code) or `CODEX_SESSION_ID`/`CODEX_THREAD_ID` (Codex); without them it shows the most recent Claude session for the working directory and notes that this is a guess. The Claude Code status line adds a segment after the cost with the session's model shares by tokens (main + subagents), e.g. `Opus 62%·Sonnet 38%`, omitted with fewer than two models at 1% or more; it is parsed incrementally with a cache in `CLAUDE_STATUSLINE_CACHE` or `<tempdir>/claude-statusline-cache`.
- User-level agent config (`user-config`): templates in `defaults/config/` (a file at the same path under `<data>/config/` replaces the engine's) are merged into `$CODEX_HOME` (default `~/.codex`) and `$CLAUDE_CONFIG_DIR` (default `~/.claude`): `codex/developer-instructions.md` becomes a marked block (`# vault-engine:begin` / `# vault-engine:end`) inside `developer_instructions` in `config.toml`, `codex/default.rules` a marked block in `rules/default.rules`, and `claude/settings.json` is deep-merged into `settings.json` (objects merge, lists are unioned, nothing is removed). Also supported: `codex/config.toml` (plus `config.windows.toml` / `.linux` / `.darwin` for that platform) whose keys and tables are upserted into `config.toml` without deleting or reformatting anything else (equivalent Windows path keys are reused, not duplicated), and `workspace/AGENTS.md` / `workspace/CLAUDE.md`, written as a `<!-- vault-engine:begin -->` / `<!-- vault-engine:end -->` block into the workspace folder (the data repo's parent). Example vault layout: `config/codex/{developer-instructions.md,default.rules,config.toml,config.windows.toml}`, `config/claude/settings.json`, `config/workspace/{AGENTS.md,CLAUDE.md}`. Placeholders `{VAULT_DATA}`, `{VAULT_ENGINE}`, `{WORKSPACE}` (the data repo's parent folder) expand to absolute paths with forward slashes; `{VAULT_DATA_NATIVE}`, `{VAULT_ENGINE_NATIVE}`, `{WORKSPACE_NATIVE}` use the OS separator (escaped per target: Codex rules, JSON). `python tools/graph.py user-config` reports drift (exit 1 if any); `--install` applies it, backing up each file as `<name>.bak-<YYYYMMDD-HHMMSS>` before its first change and changing nothing the second time. `doctor` shows a line per template and `context` prints one warning when a config dir exists and differs. See [Updating another computer](#updating-another-computer).
- Reinforce reminder: the `reinforce-check` Claude Code `Stop` hook blocks once per task id when a turn ends with `git commit`, `git push` or `gh pr create` and a task id from this session's own `context` call (ids in other tool results are ignored) has no `reinforce --task <id>` yet; when a finish signal follows a `reinforce --task <id>` without `--outcome`, it also blocks once per task and session (`blocked-no-outcome`) and asks for a note-less `reinforce --task <id> --outcome ok|partial|fail`; without a finish signal it only reminds. It logs a `reinforce_check` line to `.graph/usage.log` per decision and fails open.
- Worktree permissions: the `permission-request` Claude Code `PermissionRequest` hook (installed by `claude-hooks --install` / `update`, checked by `doctor`) allows tool calls that match `permissions.allow` (or the data repo's `permissions.worktree_allow`) inside a git worktree, denies other requests from subagents with a reason, and makes no decision for the main session (you are prompted). Each outcome is logged as `permission_allow` / `permission_deny` / `permission_prompt` in `.graph/usage.log`. `VAULT_PERMISSION_HOOK=off` disables it. See [agent-setup](agent-setup.md).
- Transcript usage metrics: plain `python tools/graph.py stats [--no-transcripts] [--projects-dir <dir>] [--json]` also scans `<Claude config dir>/projects` (measurement only; transcript text is never stored or printed). The note table gains an `opened` column: the number of transcripts (main sessions and subagent runs) that, after their first `graph.py ... context` call, opened the note with `graph.py show --body <id> [<id>...]` or a Read of a file under the vault data root (`$VAULT_DATA`; the note id is the path relative to it without `.md`). A second table lists, per project slug, main sessions, sessions with at least one `context` call and the ratio, with a total. Sessions with fewer than 3 assistant turns are skipped (the count is printed); slugs containing `claude-lab-runs` or `lab-orch` are marked `(lab)` and excluded from the total. `--no-transcripts` skips the scan (about 40 s on large transcript sets); `--json` prints `context_calls`, `closed_by_reinforce`, `retrieved`, `used`, `subagent_budgets` and `transcripts`. Codex transcripts are not read. When `subagent_stop` events carry budget fields (written by the Claude `subagent-log` hook), a "subagent budgets" section lists per role (`agent_type`) the count `n`, p50/p90 turns and tokens, `warn` and `hit` as numbers of workers (not events): `warn` = workers whose highest level was >=80% of the role's turn cap, `hit` = workers that went over the limit (a worker that resumes after a block and logs a second stop counts once; identity is `agent_id`, else `session`+`agent_type`). `n` and the percentiles stay per event.
- Channels view: plain `stats` prints a `channels:` table with Claude and Codex side by side (runs, input, cache, output, turns) and `--json` adds `channels: {claude, codex}`. Codex comes from the `codex_exec` events `codex-worker` writes to `usage.log` (sums, `reasoning`, and a `by_profile` breakdown such as `worker-low`/`worker-medium`). Runs logged with `events_missing: true` or null token fields are unknown: they count in `runs_missing_events` and are left out of the sums. Claude comes from `subagent_stop` events (internal and probe records skipped): runs, turns and total tokens; `usage.log` has no Claude input/cache/output split, so those cells are `-`/`null` (use `stats --tokens` for transcript-based Claude numbers). With no Codex events the Codex column shows zero runs.
- Embedding errors: when Ollama answers HTTP 400 to the batched `/api/embed` request (`context`, `index`), the query is embedded alone so the semantic path stays on, and the note chunks are bisected to find what Ollama refuses. A refused chunk of any size is split in two at whitespace (never truncated; the second half repeats the context prefix up to the first `": "`) and both halves are retried recursively, down to about 50 characters of text. At that floor it is retried once with control characters and invalid Unicode removed; if that is refused too, only that piece is skipped: its index goes in the `skipped` list of the note's entry in `.graph/embeddings.json` (so it is not retried every run), one `embed_skipped` event (`note`, `chunk`, `reason`) goes to `usage.log`, `warning:` on stderr names the note id and chunk number (never text), and `doctor` prints a `WARN` for the note. The note stays findable by keyword. Other errors (404, connection, timeout) still fall back to keyword-only with no retry.
- Retrieval health: `python tools/graph.py stats --retrieval [--since YYYY-MM-DD] [--until YYYY-MM-DD] [--json]` reads `.graph/usage.log` and prints precision and coverage proxies (reinforced vs loaded notes, macro and micro), the share of reinforced notes that were omitted, `show` pulls, keyword-fallback rate (deliberate vs failure, plus a `by reason` line counting each logged `fallback_reason`; events without one count as `unspecified`; `--json` has `keyword_fallback.by_reason`), mean learned share and closure; events lacking a metric's fields are skipped and each line reports its sample size.
- Delegation metrics: the `delegation-warn` hook (Claude Code and Codex log the same events) appends one `orchestrator_prompt` line to `.graph/usage.log` per finished user message (main-thread tool calls, whether the warning fired). `python tools/graph.py stats` then prints an `orchestrator prompts:` line: prompts measured, how many went over the threshold (with %), and the median inline calls. When events carry `ab_arm` it adds `ab_arm warn` and `ab_arm silent` lines (mean inline calls, warned %), and one `engine <version>` line per engine version when `engine_version` is present. The last message of a session is not measured, and logs without these events print nothing extra. Entries older than 90 days (`USAGE_LOG_KEEP_DAYS` in `tools/graph.py`) are trimmed automatically: `graph.py` checks after writing its own usage event whether the oldest entry is past the cutoff (so it rewrites about once a day, no extra state file), rewrites the file atomically and keeps lines whose `ts` it cannot parse. The hooks never trim.
- Update: `python tools/graph.py update` fetches tags, shows the CHANGELOG sections between the current and the new version (including Upgrade notes), asks for confirmation, then checks out the new tag (dev channel: fast-forwards `main`, see above) and runs `migrate --yes` and `setup --yes --no-env` with the new version. Both channels then run the same steps: the `AGENTS.md` check, Claude subagent files, Codex worker profiles, Claude Code hooks, model settings, Codex hooks, and finally `doctor`. It never changes environment variables or shell startup files; run `setup` yourself if the Upgrade notes ask for it. If the Claude Code hooks are missing (and `~/.claude` exists), it then offers `claude-hooks --install`: in a terminal it asks, with `--claude-hooks` it installs without asking, and with `--yes` alone it only prints the command. It then does the same for the Claude Code model settings (`settings.json`, `worker-*.md`) via `models`/`models --apply`, offering it with `--models` or an interactive yes. It then does the same for `~/.claude/agents/*.md` that differ from the engine's current versions (via `setup`'s agent step), offering it with `--agents` or an interactive yes.
  - `--check`: only reports whether a newer version exists.
  - `--to <tag>`: switches to a specific version, including an older one; going back is refused if the vault was already migrated to a newer data schema.
  - `--yes`: skips the confirmation prompt. It never writes `~/.claude` or `~/.codex` by itself.
  - `--all`: consent for every user-level write without prompts (Claude agents, Claude and Codex hooks, model settings, Codex workers); implies `--yes`. `AGENTS.md` still needs `--apply-agents`. The per-step flags (`--claude-hooks`, `--models`, `--agents`, `--codex-hooks`) keep working.
  - `--apply-agents`: replaces the data repo's `AGENTS.md` with the engine's `templates/AGENTS.md`, after showing the diff, and commits it. It also works when the engine is already up to date (for example after a manual upgrade) or on the dev channel. Without the flag, `update` shows the diff only when the file is behind the template, and replaces it only after a yes on the interactive prompt. The template ends with a `vault-engine AGENTS.md template: N` line: keep it when you translate or edit your `AGENTS.md`, and the file counts as current until a newer template revision comes out. `doctor` warns when the file is behind.
  - `--models`: syncs Claude Code's model settings (`models --apply`) without asking, if they are out of date.
- `vault.config.json` has a `"schema": <int>` field (the vault's data layout version; missing means `1`). An engine of 0.3.0 or later that is older than the vault's schema refuses commands that write shared data (`reinforce`, `decay`, `mv`, `onboard`, `init`, `feedback set`) but `context` still works, and it asks to run `update` on that computer — useful when two computers share one vault and update at different times. Engines 0.1.0 and 0.2.0 predate this check: they write to any vault (their `init` even drops the `"schema"` field), so every computer sharing a vault must be on 0.3.0 or later before any of them installs a release that raises the schema. `python tools/graph.py migrate [--yes] [--dry-run] [--no-commit]` upgrades an older vault to the current schema, records a missing `"schema"` field and moves a shared `project_roots` to this computer's `.graph/machine.json`, then makes one commit in the data repo with only its own files (anything else already staged stays staged; never pushes). `--dry-run` shows the plan without writing. If `vault.config.json` has uncommitted edits of your own, `migrate` leaves it untouched and asks you to commit them first; a rerun after `--no-commit` commits the earlier result. `migrate` also appends any line of `templates/.gitignore` that the vault's `.gitignore` lacks (append only, never removing or reordering yours; a `!X` line keeps `X` out) in a separate commit, and skips it with a warning while `.gitignore` has uncommitted edits.
- **Updating from 0.1.0 or 0.2.0**: these versions have no `update` or `migrate` command (`invalid choice: 'update'`) and never announce new versions. Update once by hand in the engine folder; after that, `update` works:
  1. `git status --porcelain` must print nothing; then `git fetch --tags origin` and `git tag --list "v*" --sort=-v:refname` (the first line is the newest release).
  2. Read the new sections of `git show <new tag>:CHANGELOG.md`, above all the Upgrade notes.
  3. `git checkout <new tag>`, then `python tools/graph.py migrate --yes`, `python tools/graph.py setup --data <data repo> --yes` and `python tools/graph.py doctor` (what `update` runs after switching).
  4. Fix what `doctor` warns about. If it says the vault CI runs an old engine ref, run `python tools/graph.py update` (already up to date, it re-pins `.github/workflows/vault.yml`); if `vault.yml` still says `vault-engine@main` and `doctor` doesn't warn, change it to `@<new tag>` by hand. If it says `AGENTS.md` is behind the template, `python tools/graph.py update` shows the diff and `update --apply-agents` replaces the file.
  5. Commit and push the data repo, then do the same on every other computer that shares it.

  The agent-facing version of these steps is in [docs/agent-setup.md](agent-setup.md), "Updating from 0.1.0 or 0.2.0".
- Maintainers: bump `__version__` in `tools/graph.py`, add a CHANGELOG entry, merge, then tag `vX.Y.Z` and create a GitHub release. A test fails if HEAD is tagged `vX.Y.Z` but `__version__` differs. If the release raises `SCHEMA_VERSION` in `tools/schema.py`, its Upgrade notes must first say to bring every computer that shares the vault to 0.3.0 or later before migrating on any of them, and must name the new schema (`schema N`): 0.1.0 and 0.2.0 have no schema check and would write to the migrated vault. A test checks that the CHANGELOG has such a note for each schema above 1.

## Contributing to the engine
- Run `git config core.hooksPath .githooks` in this repo. `leakcheck` blocks commits containing user content (`profile/`, `projects/`, ...), the home directory path, the git identity, or terms from `.git/info/vault-denylist`.
- New code should come with tests.
